# SDDの実施手順

## 1. この文書の使い方

この文書では、一つの要件を開始してから、GitHubのPull Requestを通じて `main` へマージし、ローカルを同期するまでの標準手順を説明します。

この手順は、機能、公開契約、インフラ構成などを変更するSDD対象の要件に適用します。誤字やリンクの修正、動作を変えない整形、軽微なリポジトリ保守、変更を伴わない調査などは、実行時の挙動に影響しないことを確認できる場合に限り、SDD成果物を省略できます。

本書で「承認」とは、チームメンバーが会話またはレビュー記録で成果物の承認と次段階への進行を明示した状態を指します。ファイルが存在することだけを理由に、レビュー済みまたは承認済みとは扱いません。

例では、次のfeature directoryとブランチを使用します。

```text
feature directory: specs/001-example-feature
branch: feature/001-example-feature
alternative branch: 02-agent-core-basic-01
```

開発支援AIへの入力方法はツールごとに異なるため、以下の依頼例ではSkill名を文章で明示しています。

## 2. Step 0: 要件を分割する

作業を開始する前に、要件が一つのfeature directory、一つのブランチ、一つのPull Requestでレビューできる大きさか確認します。

分割を検討する例:

- 独立した目的や受け入れ条件が複数ある
- 変更領域が多く、レビュアーが一度に全体を確認しにくい
- 一部だけを先にリリースまたは検証できる
- 複数の設計判断を同時に行う必要があり、議論を分けた方が明確になる
- 一つのPull Requestとして差分が大きすぎる

要件を分割する場合は、feature directory、ブランチ、Pull Requestも分けます。

## 3. Step 1: mainを最新化して要件ブランチを作成する

### 3.1 mainを最新化する

```bash
git status --short
git switch main
git pull --ff-only origin main
```

作業ツリーに未コミットの変更がある場合は、そのままブランチを切り替えたり、pullしたりしません。内容を確認し、自分が作成していない差分を勝手に破棄しません。

### 3.2 要件ブランチを作成する

```bash
git switch -c feature/001-example-feature
```

- 新しい要件には `feature/NNN-short-feature-name`、要件番号と追加対応の連番を示す場合は `NN-short-feature-name-NN` の形式を使用できます。
- 後者の例は `02-agent-core-basic-01` です。
- `main` 上でSDD成果物や実装を変更しません。
- 一つの要件ブランチに、複数の独立した要件を混在させません。
- 既存のマージ済みブランチを新しい要件に再利用しません。

## 4. Step 2: feature directoryとspec-draft.mdを作成する

### 4.1 feature directoryを作成する

プロジェクトの命名規則に従い、feature directoryを作成します。

```text
specs/001-example-feature/
└── spec-draft.md
```

### 4.2 spec-draft.mdに下書きを記載する

`spec-draft.md` は、要求や会話の内容を最初から完全な仕様にするための文書ではありません。現時点で分かっていることと、まだ決まっていないことを区別して記載します。

記載例:

```markdown
# Example feature draft

## 要望

- 利用者が処理結果を確認できるようにしたい。

## 背景

- 現在は処理が成功したかをログから確認している。

## 現時点で分かっていること

- 既存の認証方式を使用する。
- 対象は新規処理のみとする。

## 未確定事項

- 結果を画面で表示するか、APIで返すか。
- 保存期間をどの程度にするか。
```

会話で要件を整理している場合は、合意した内容と未確定事項を `spec-draft.md` に反映してから、仕様書作成へ進みます。

## 5. Step 3: specs.mdを作成する

### 5.1 create-sdd-specを使用する

依頼例:

```text
create-sdd-spec Skillを使用し、
feature directory `specs/001-example-feature` の `specs.md` を作成してください。
実装、plan.md、tasks.md、ADRの作成は行わないでください。
```

`create-sdd-spec` は、`spec-draft.md` と既存コード・設定・文書を確認し、次を整理します。

- 概要、背景、目的
- スコープと対象外
- ユーザーストーリーまたは利用シナリオ
- 機能要件、非機能要件
- 受け入れ条件
- 制約、依存関係
- 未確定事項、要確認事項

### 5.2 specs.mdをレビューする

次の段階へ進む前に、最低限次を確認します。

- 目的とスコープが一致しているか
- 対象外が明確か
- 要件が複数の意味に解釈されないか
- 受け入れ条件をテストまたは確認できるか
- 実装方法が仕様に混入していないか
- 未確定事項が確定事項として書かれていないか

レビューで要件が変わった場合は、`spec-draft.md` と `specs.md` を更新します。仕様が合意される前に `plan.md` や実装へ進みません。

## 6. Step 4: plan.mdを作成する

### 6.1 create-sdd-planを使用する

依頼例:

```text
create-sdd-plan Skillを使用し、
feature directory `specs/001-example-feature` の `plan.md` を作成してください。
既存コード、設定、テスト、関連文書を確認し、実装は行わないでください。
```

`plan.md` では、`specs.md` の要求を変更せず、次を整理します。

- 実装全体の方針
- 変更対象と変更しないもの
- 既存パターンの再利用と新規要素の要否
- データ、API、イベント、設定、インフラ、運用への影響
- リスク
- 受け入れ条件に対応する検証方針
- 更新が必要な文書とADRの要否
- 実施順序
- 未解決事項

### 6.2 plan.mdをレビューする

次を確認します。

- `specs.md` の要求を追加・変更していないか
- 変更対象と変更しないものが区別されているか
- 既存の実装パターンを確認しているか
- 新しい技術や依存関係を導入する理由があるか
- リスクと検証方針が具体的か
- 受け入れ条件と検証方法が対応しているか
- 実施順序が現実的か
- ADRの要否が整理されているか

未解決事項が実装開始を妨げる場合は、先に解決します。

## 7. Step 5: 設計判断をADRに記録する

### 7.1 ADRを作成するタイミング

ADRは、SDDの特定の段階に限定して作成するものではありません。要求整理、仕様作成、実装計画、実装中のいずれであっても、次のような設計判断が確定した時点で記録します。

- 複数の選択肢から一つの方式を選んだ
- システム構成や責務の分担を決めた
- 将来の開発や運用に影響するルールを決めた
- 後から「なぜこの方式を選んだのか」を説明する必要がある
- 採用しない方式と、その理由を残す必要がある

単なる実装手順や一時的な作業メモはADRにしません。

### 7.2 create-sdd-adrを使用する

依頼例:

```text
create-sdd-adr Skillを使用し、
ここまでの会話で合意した「<設計判断>」を一つのADRとして作成してください。
会話で決まっていない内容は推測せず、未決事項として残してください。
```

ADRの入力は、現在の会話で合意された内容、会話中に提示された情報、明示的に参照された資料などです。特定のファイルを必須の入力元にはしません。

構成や処理フローを図で示した方が理解しやすい場合は、Mermaidを使用します。

## 8. Step 6: tasks.mdを作成する

### 8.1 create-sdd-tasksを使用する

依頼例:

```text
create-sdd-tasks Skillを使用し、
feature directory `specs/001-example-feature` の `tasks.md` を作成してください。
実装は行わず、各タスクに対象、実施内容、完了条件、依存関係を記載してください。
```

`tasks.md` には、次の区分でタスクを作成します。

- 前提確認
- 実装
- テスト・検証
- ドキュメント更新
- 完了確認

実装タスクの見出しは、固定された技術領域名ではなく、`plan.md` の実際の変更対象から作成します。

各タスクは、次の条件を満たす必要があります。

- 一つの目的に集中している
- 実装可能な粒度である
- 完了を客観的に確認できる
- 対象が分かる
- 依存タスクが分かる
- `specs.md` または `plan.md` に根拠がある

並列に実施できるタスクには `[P]` を付けます。

### 8.2 tasks.mdをレビューする

- 実装順と依存関係が正しいか
- 一つのタスクに複数の独立した成果が混ざっていないか
- 単独では成果を確認できないほど細かく分割されていないか
- 実装と検証が同じタスクに混ざっていないか
- すべての受け入れ条件を確認できるか
- ドキュメント更新が漏れていないか
- 図が必要な文書更新にMermaid作成・更新が含まれているか

## 9. Step 7: tasks.mdに従って実装する

実装担当者は、タスクIDと対象を確認して作業を開始します。

共同開発では、次を守ります。

- 依存タスクが完了していない場合は、前提を確認せずに着手しない
- `[P]` が付いたタスクでも、同じファイルやリソースを変更する場合は担当者間で調整する
- 実装中に仕様変更が必要になった場合は、コードだけを変更せず、上流成果物へ戻る
- 実装中に新しい設計判断が生じた場合は、必要に応じてADRを作成する
- 完了したタスクは、チームの運用ルールに従って `[x]` に更新する

## 10. Step 8: テスト・検証とドキュメント更新を行う

`tasks.md` に定義されたテストと検証を実施します。

- 実施したコマンドと結果を確認する
- 実施できない検証がある場合は、対象と理由を記録する
- 実行していないテストを完了扱いにしない
- READMEや `docs/` を現在の実装と一致させる
- 図で示した方が理解しやすい場合はMermaidを追加または更新する
- Mermaid図の内容と本文が一致していることを確認する

## 11. Step 9: 変更をコミットする

コミットは、要件の最後に一度だけ作成するのではなく、意味のある変更単位で作成します。

### 11.1 コミットする差分をステージする

対象ファイルを確認し、今回のコミットに含める差分だけをステージします。

```bash
git status --short
git diff
git add <files>
git diff --cached
```

- 一つのコミットに複数の独立した目的を混在させません。
- 未追跡ファイル、シークレット、認証情報、一時ファイルが含まれていないことを確認します。
- `git add .` を使用する場合も、ステージ済み差分を必ず確認します。

### 11.2 create-commit-messageを使用する

依頼例:

```text
create-commit-message Skillを使用し、
現在のステージ済み差分に対応するコミットメッセージを作成してください。
git commitは実行しないでください。
```

このSkillは、主に次を確認します。

```bash
git branch --show-current
git status --short
git diff --cached --name-status
git diff --cached --stat
git diff --cached
git log -5 --oneline
```

コミットメッセージは、`git diff --cached` のステージ済み差分だけを説明します。未ステージの変更やブランチ全体の内容を含めません。

例:

```text
docs(sdd): AgentCore Gatewayの仕様と実装計画を追加
```

```text
feat(cdk): AgentCore Gatewayリソースを追加
```

```text
test(cdk): Gateway構成のsynthテストを追加
```

### 11.3 メッセージを確認してコミットする

作成されたメッセージが実際のステージ済み差分と一致することを確認してから、コミットします。

```bash
git commit -m "<commit message>"
```

本文を含む場合は、エディタまたは複数の `-m` オプションなど、チームの運用に合う方法を使用します。

実装、テスト、文書更新が続く場合は、Step 7からStep 9を必要な回数だけ繰り返します。

## 12. Step 10: 要件全体の完了確認を行う

ブランチをpushする前に、次を確認します。

- `specs.md` の受け入れ条件を満たしている
- `plan.md` の実装方針と変更対象に沿っている
- `tasks.md` の必要なタスクが完了している
- 対象外の変更が混ざっていない
- 必要なテストと検証が完了している
- 未実施の検証理由が記録されている
- README、docs、ADRが現在の実装・判断と一致している
- シークレット、認証情報、一時ファイル、不要ファイルが差分に含まれていない
- コミットされていない必要な変更が残っていない

確認例:

```bash
git status --short
git log origin/main..HEAD --oneline
git diff --stat origin/main...HEAD
```

`origin/main` が最新か確認できない場合は、その制約を把握した上でレビュー依頼します。

## 13. Step 11: 要件ブランチをGitHubへpushする

要件全体がレビュー可能な状態になったら、ブランチをpushします。

初回:

```bash
git push -u origin feature/001-example-feature
```

2回目以降:

```bash
git push
```

- `main` へ直接pushしません。
- 原則として `git push --force` は使用しません。
- push後に追加修正した場合は、必要なコミットを作成して再度pushします。

## 14. Step 12: Pull Requestメッセージを作成する

### 14.1 create-pull-request-messageを使用する

依頼例:

```text
create-pull-request-message Skillを使用し、
現在の要件ブランチからmainへのPull Requestタイトルと本文を作成してください。
Pull Request自体は作成しないでください。
```

このSkillは、主に次を確認します。

```bash
git branch --show-current
git status --short
git log origin/main..HEAD --oneline
git diff --name-status origin/main...HEAD
git diff --stat origin/main...HEAD
git diff origin/main...HEAD
```

必要に応じて、差分に含まれるfeature directory、SDD成果物、ADR、README、`docs/`、確認済みの検証結果も整理します。

### 14.2 コミットメッセージとの違いを確認する

- コミットメッセージは、一つのコミットに含まれるステージ済み差分を説明します。
- Pull Requestタイトルと本文は、`main` と要件ブランチの差分全体を説明します。
- PR本文をコミットメッセージの一覧だけにしません。
- 実行していない検証を、完了済みとして記載しません。

PRタイトル例:

```text
feat(cdk): AgentCore GatewayをAWS CDKで構築
```

PR本文には、確認できる範囲で次を記載します。

- 概要
- 背景・目的
- 変更内容
- SDD成果物
- 対応タスク
- 検証結果と未実施理由
- レビュー観点
- 対象外
- 関連Issue、ADR、文書
- 未確定事項、後続課題

## 15. Step 13: Pull Requestを作成する

作成されたタイトルと本文を確認し、GitHubで `main` に対するPull Requestを作成します。

- Pull Requestの差分が想定した要件だけであることを確認します。
- レビュアーが実行結果を確認できるよう、検証結果を具体的に記載します。
- 未解決事項や後続課題を隠しません。
- 複数の独立した要件が混在している場合は、無理に一つのPull Requestにせず分割します。

## 16. Step 14: レビューを受けてmainへマージする

Pull Requestでは、SDD成果物、実装、テスト、文書を含む要件全体をレビューします。

- 指摘によって要件、実装方針、タスク、設計判断が変わる場合は、対応するSDD成果物も更新します。
- 修正後は、必要なテストと検証を再実施します。
- 修正コミットをpushし、PR本文の検証結果や未解決事項も更新します。
- マージ権限を持つ管理者または指定レビュアーが、レビュー完了後に `main` へマージします。
- Pull Requestを経由せず、直接 `main` へ変更を反映しません。

## 17. Step 15: マージ後にローカルmainを更新する

Pull Requestがマージされたら、ローカルリポジトリを更新します。

```bash
git status --short
git switch main
git pull --ff-only origin main
```

- マージ済みの要件ブランチは、ローカル、リモートとも削除せずに保持します。
- 保持したブランチを、新しい要件の作業に再利用しません。
- 次の要件では、更新後の `main` から新しい要件ブランチを作成します。
- マージ後に不足していた小規模な対応を追加する場合も、最新の `main` から末尾の連番を変えた新しいブランチを作成します。

## 18. 途中で変更が発生した場合

変更内容に応じて、上流成果物から修正します。

| 変更内容 | 最初に見直す成果物                    | その後に確認する成果物                          |
|---|------------------------------|--------------------------------------|
| 目的、スコープ、要件、受け入れ条件が変わる | `spec-draft.md` / `specs.md` | `plan.md`、`tasks.md`、必要なADR          |
| 実装方式、変更対象、検証方針が変わる | `plan.md`                    | `tasks.md`、必要なADR                    |
| 作業順、担当可能な単位、依存関係だけが変わる | `tasks.md`                   | 実装状況                                 |
| 設計判断や判断理由が変わる | ADR                          | `specs.md`、`plan.md`、`tasks.md` への影響 |
| ステージ済み差分の目的が混在する | ステージ内容                       | コミットの分割                              |
| ブランチに独立した複数要件が混在する | 要件分割                         | feature directory、ブランチ、Pull Request  |

下流の成果物だけを修正し、上流の成果物との矛盾を残さないでください。

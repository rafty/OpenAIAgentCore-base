# Commit Message作成Skill

## 目的

現在のブランチにおけるステージ済み差分だけを根拠に、単一または複数の変更目的を適切に要約したコミットメッセージを作成する。

## 入力

主な入力は、現在のGitリポジトリとステージ済み差分である。

必要に応じて、会話中に明示された次の情報も使用できる。

- 対象feature directory
- 対応する `tasks.md` のタスクID
- 変更理由や注意事項
- リポジトリ固有のコミット規則

## 出力

`assets/commit-message-template.md` の形式に従い、原則として一つの推奨コミットメッセージを出力する。

## 最初に確認すること

次の順序で確認する。

1. リポジトリのルートと適用される `AGENTS.md`
2. 現在のブランチ
3. 作業ツリーとステージの状態
4. ステージ済みファイルの一覧と差分
5. 既存コミットのメッセージ形式

確認に使用する代表的なコマンド:

```bash
git branch --show-current
git status --short
git diff --cached --name-status
git diff --cached --stat
git diff --cached
git log -5 --oneline
```

## 作業手順

1. 現在のブランチが要件ブランチであることを確認する。
2. `git diff --cached` にステージ済み差分があることを確認する。
3. ステージ済み差分に含まれる変更目的を整理する。
4. 中心的な目的またはコミット全体を最も適切に表すtypeを選択する。
5. 必要な場合だけscopeを付ける。
6. 変更内容を簡潔な日本語のsummaryにする。
7. 複数の変更目的がある場合、またはsummaryだけでは理由や影響が分からない場合は本文を付ける。
8. タスクIDや破壊的変更など、必要な情報だけfooterへ記載する。
9. テンプレートに従ってメッセージを作成する。
10. 出力前にメッセージとステージ済み差分の一致を確認する。

## typeの選択

原則として次を使用する。

- `feat`: 利用者またはシステムに新しい機能を追加する
- `fix`: 不具合を修正する
- `docs`: 文書だけを追加または変更する
- `test`: テストだけを追加または変更する
- `refactor`: 外部挙動を変えずに実装構造を改善する
- `perf`: 性能を改善する
- `build`: ビルドや依存関係を変更する
- `ci`: CI設定やCI処理を変更する
- `chore`: 上記に該当しない保守作業を行う
- `style`: 挙動に影響しない整形を行う
- `revert`: 既存コミットを取り消す

typeは差分の中心的な目的に合わせる。複数の独立した目的が含まれる場合は、コミット全体を最も適切に表すtypeを選択する。

- 新機能がコミット全体の中心で、文書や開発支援設定がその実装を支える場合は `feat` を使用できる。
- 文書だけで構成される場合は `docs` を使用する。
- 開発支援設定、文書、機能などが並列に含まれ、単一のtypeで表しにくい場合は `chore` を使用できる。
- 複数目的であることだけを理由に、コミットメッセージの作成を中止しない。

## メッセージ形式

基本形式:

```text
<type>(<scope>): <summary>
```

scopeが不要な場合:

```text
<type>: <summary>
```

本文が必要な場合は、空行を挟んで変更理由、影響、注意事項を書く。複数の変更目的がある場合は、本文の箇条書きで主要な変更群を整理する。

破壊的変更の場合は、typeまたはscopeの後ろに `!` を付け、footerに `BREAKING CHANGE:` を記載する。

## 作業ルール

- コミットメッセージは、ステージ済み差分だけを説明する。
- 未ステージの変更や未追跡ファイルを、コミット済みの変更として含めない。
- コミットメッセージの作成依頼は、`git commit` の前に行われる通常の手順として扱う。
- `AM` や `MM` など、ステージ後の未ステージ変更が存在しても、メッセージ作成を中止しない。
- ステージ後の未ステージ変更がある場合は、メッセージがステージ済み版だけを根拠としていることと、作業ツリーの最新版は含まれないことをメッセージの外で簡潔に報告する。
- ユーザーが作業ツリーの最新版も同じコミットへ含める意図を示している場合は、コミット前に対象をステージし直す必要があることを報告する。ただし、明示的に依頼されない限り `git add` は実行しない。
- ステージ済み差分がない場合は、コミットメッセージを作成しない。
- 現在のブランチが `main` の場合は、その事実を報告し、プロジェクトルール上の例外が明示されていなければ作成を中止する。
- summaryは簡潔にし、末尾に句点を付けない。
- 「変更」「対応」「修正」だけで終わる曖昧なsummaryを作成しない。
- scopeは実際のコンポーネント、モジュール、文書領域などを表せる場合だけ付ける。
- 固定されたscopeを推測で使用しない。
- 実行していないテストや検証を本文に記載しない。
- 明示的に依頼されない限り、`git add`、`git commit`、`git push` を実行しない。
- Pull Requestのタイトルや本文は作成しない。

## 出力ルール

- 原則として、コピーして使用できる一つの推奨メッセージをコードブロックで出力する。
- 複数の独立した目的が含まれる場合も、一つの推奨メッセージを作成し、必要に応じて本文で変更群を整理する。
- コミット分割は、ユーザーが希望した場合、履歴の理解が著しく難しくなる場合、または一部だけを安全に取り消す必要性が明確な場合に、任意の提案として示す。分割をメッセージ作成の必須条件にはしない。
- 判断に必要な情報が差分から確認できない場合は、推測せず不足情報を示す。

## 自己レビュー

出力前に次を確認する。

- メッセージが `git diff --cached` の内容だけを表しているか。
- typeが変更の中心的な目的と一致しているか。
- scopeが実際の変更対象と一致しているか。
- summaryから何を変更したか分かるか。
- 本文やfooterに未確認の情報が含まれていないか。
- 複数の変更目的がある場合、summaryと本文で主要な変更群を過不足なく説明しているか。
- リポジトリの既存メッセージ形式と大きく矛盾していないか。

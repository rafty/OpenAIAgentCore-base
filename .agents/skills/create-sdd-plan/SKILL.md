# SDD Plan作成Skill

## 目的

`spec.md` をもとに、仕様を実現するための実装方針を整理した
`plan.md` を作成する。

## 入力

ユーザーから対象feature directoryを受け取る。

入力例:

```text
specs/001-requirement
```

入力ファイル:

```text
<feature-directory>/spec.md
```

出力ファイル:

```text
<feature-directory>/plan.md
```

## 最初に確認すること

次の順序で既存情報を確認する。

1. 対象feature directory
2. 対象ディレクトリに適用されるAGENTS.md
3. spec.md
4. 対象領域のREADME.md
5. 関連する既存コードと設定
6. docs/配下の関連文書
7. 既存のADR
8. 関連するテスト、ビルド、デプロイ、検証の仕組み

`spec.md` の要求と受け入れ条件を確認し、推測ではなく、既存コード、
既存設定、既存文書、既存の実装パターンに基づいて計画を作成する。

## 作業手順

1. spec.mdから目的、スコープ、機能要件、非機能要件、受け入れ条件、制約、依存関係、未確定事項を抽出する。
2. 単一領域のfeatureか、複数領域にまたがるfeatureかを判定する。
3. 既存コードと設定を確認し、再利用できる実装パターンを特定する。
4. 変更対象と変更しない対象を明確にする。
5. 技術方針と領域ごとの責務分担を整理する。
6. DB、API、イベント、設定値、Secret、インフラ、デプロイ、運用への影響を確認する。
7. 互換性、破壊的変更、セキュリティ、運用、監視などのリスクを整理する。
8. spec.mdの受け入れ条件を満たすための検証方針を定義する。
9. README.md、docs/、ADRなどの文書更新要否を判定する。
10. 実装を進める段階的な順序を整理する。
11. `assets/plan-template.md` の形式に従って `plan.md` を作成する。
12. 作成後に内容を自己レビューする。

## 作業ルール

- `plan.md` では「どう作るか」を整理する。
- spec.mdに記載された要求を変更、追加、再定義しない。
- 実装方針、分割方針、影響範囲、検証方針を中心に記載する。
- 未確認の内容を確定した事実として記載しない。
- 判断できない点は「未解決事項」または「要確認」として記載する。
- 既存コードと既存構成のパターンを優先する。
- 新しい方式、依存関係、コンポーネントを導入する場合は、その理由を書く。
- 複数領域にまたがる場合は、領域ごとの変更内容と責務分担を明記する。
- 既存インフラや既存契約を参照するだけの場合は、変更しないことを明記する。
- 実装は行わない。
- spec.mdは変更しない。
- tasks.mdは作成しない。
- ADRは作成しない。ADRの作成要否のみをplan.mdに記載する。

## 自己レビュー

出力前に次を確認する。

- spec.mdの目的、スコープ、要件、受け入れ条件と整合しているか。
- 要求の追加や再定義を行っていないか。
- 変更対象と変更しない対象が区別されているか。
- 単一領域か複数領域かが明記されているか。
- 複数領域の場合、責務分担と実施順序が明確か。
- データ、API、イベント、設定、インフラ、運用への影響を確認しているか。
- リスクとその確認方法が具体的か。
- 検証方針が受け入れ条件に対応しているか。
- ADRを含む文書更新の要否が整理されているか。
- 未確認事項が確定事項として混入していないか。
- テンプレートの必須項目が欠けていないか。

## 完了時の報告

次の内容を簡潔に報告する。

- 作成したファイル
- 主な実装方針
- 主な変更対象
- 主なリスクと検証方針
- ADRの作成要否
- tasks作成前に確認が必要な事項

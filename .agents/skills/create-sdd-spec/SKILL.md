# SDD Spec作成Skill

## 目的

`spec-draft.md` をもとに、実装前のfeature仕様書
`spec.md`を作成する。

## 入力

ユーザーから対象feature directoryを受け取る。

入力例:

```text
specs/001-requirement
```

入力ファイル:

```text
<feature-directory>/spec-draft.md
```

出力ファイル:

```text
<feature-directory>/spec.md
```

## 最初に確認すること

次の順序で既存情報を確認する。

1. 対象feature directory
2. 対象ディレクトリに適用されるAGENTS.md
3. spec-draft.md
4. 対象領域のREADME.md
5. 関連する既存コードと設定
6. docs/配下の関連文書
7. 既存のADR

推測ではなく、既存コード、既存設定、既存文書に基づいて整理する。

## 作業手順

1. spec-draft.mdから要求を抽出する。
2. 確定済み事項と未確定事項を分ける。
3. 機能要件と非機能要件を分ける。
4. 対象範囲と対象外を明確にする。
5. 受け入れ条件を検証可能な形式で定義する。
6. 関連コードと既存構成との依存関係を確認する。
7. 単一領域の変更か複数領域の変更かを明記する。
8. `assets/spec-template.md` の形式に従って `spec.md` を作成する。
9. 作成後に内容を自己レビューする。

## 作業ルール

- 実装方法ではなく、満たすべき要求を中心に記載する。
- 未確定事項を確定した事実として記載しない。
- 既存コードや文書から確認できない内容を推測しない。
- 必要に応じて対象外を明記する。
- 実装は行わない。
- plan.mdは作成しない。
- tasks.mdは作成しない。
- ADRは作成しない。
- spec-draft.mdは変更しない。

## 自己レビュー

出力前に次を確認する。

- 目的と機能要件が整合しているか。
- 各受け入れ条件が検証可能か。
- スコープと対象外が矛盾していないか。
- 未確定事項が要件に混入していないか。
- 実装詳細を過剰に規定していないか。
- 関連領域と依存関係が明記されているか。
- テンプレートの必須項目が欠けていないか。

## 完了時の報告

次の内容を簡潔に報告する。

- 作成したファイル
- 主な仕様
- 未確定事項
- plan作成前に確認が必要な事項

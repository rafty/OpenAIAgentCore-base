# SDD Tasks作成Skill

## 目的

`specs.md` と `plan.md` をもとに、実装可能かつ確認可能な粒度へ分解した
`tasks.md` を作成する。

## 入力

ユーザーから対象feature directoryを受け取る。

入力例:

```text
specs/001-requirement
```

入力ファイル:

```text
<feature-directory>/specs.md
<feature-directory>/plan.md
```

出力ファイル:

```text
<feature-directory>/tasks.md
```

## 最初に確認すること

次の順序で既存情報を確認する。

1. 対象feature directory
2. 対象ディレクトリに適用されるAGENTS.md
3. specs.md
4. plan.md
5. 対象領域のREADME.md
6. 関連する既存コードと設定
7. docs/配下の関連文書
8. 既存のADR

`specs.md` の要求・受け入れ条件と、`plan.md` の実装方針・変更対象・実施順序を
タスク分解の根拠とする。

## 作業手順

1. `specs.md` からスコープ、対象外、機能要件、非機能要件、受け入れ条件、未確定事項を抽出する。
2. `plan.md` から変更対象、変更しないもの、技術方針、検証方針、実施順序、未解決事項を抽出する。
3. 未確定事項や未解決事項のうち、実装開始前に解決が必要なものを前提確認タスクにする。
4. 変更対象を領域、モジュール、設定、契約単位で整理する。
5. 実装タスクを依存関係に沿って実行可能な順序へ並べる。
6. 実装タスクと、テスト・検証タスクを分ける。
7. README、docs、ADRなどの更新要否を確認し、必要な更新だけをタスク化する。
8. READMEやdocs配下の文書について、構成、関係、処理フロー、シーケンスなどを図で示す方が理解しやすい場合は、Mermaidによる図の作成または更新をドキュメント更新タスクに含める。
9. 各受け入れ条件を、いずれかの実装タスクまたは検証タスクで確認できるようにする。
10. 並列に実施できるタスクには `[P]` を付ける。
11. `assets/tasks-template.md` の形式に従って `tasks.md` を作成する。
12. 作成後に内容を自己レビューする。

## タスク分解ルール

- タスクは実装順に並べる。
- タスク名は、何をするかが分かる動詞で始める。
- 1タスクは、できるだけ1つの目的に集中させる。
- タスクは、実装可能かつ完了を確認できる粒度にする。
- 「調査・前提確認」「実装」「テスト・検証」「ドキュメント更新」「完了確認」を分ける。
- `specs.md` にない要求や作業を追加しない。
- `plan.md` に反するタスクを追加しない。
- 対象外として定義された変更をタスク化しない。
- タスク間の依存関係が分かる順序にする。
- 並列に進められるタスクには `[P]` を付ける。
- 固定された技術領域名ではなく、`plan.md` の変更対象から実装単位の見出しを作成する。
- 実装単位は、コンポーネント、リソース、Agent、モジュール、設定、API、契約など、実際の変更対象に合わせる。
- 参照するだけで変更しない対象については、実装タスクを作成しない。
- 各実装タスクには、対象、実施内容、完了条件、依存関係を明記する。
- 1タスクが複数の独立した成果を含む場合は分割し、単独で成果を確認できない細かな編集は同じ目的のタスクへまとめる。
- 実装タスクと検証タスクを同じチェック項目に混在させない。
- 抽象的な「対応する」「必要に応じて修正する」だけのタスクを作成しない。
- 対象ファイルや対象モジュールが確認できる場合は、タスクに明記する。
- `plan.md` でADRが必要と判断されている場合だけ、ADR作成または更新をタスク化する。
- READMEや`docs/`配下の文書を更新する場合は、文章だけで十分に理解できるかを確認する。
- システム構成、コンポーネント間の関係、データフロー、処理フロー、シーケンス、状態遷移、依存関係などを図で示す方が理解しやすい場合は、Mermaid図の作成または更新をタスクに含める。
- 図を追加するだけで理解が改善しない場合や、単純な内容を文章で十分に説明できる場合は、Mermaid図を無理に追加しない。
- Mermaid図を含むタスクには、対象文書、図で説明する内容、本文との整合確認、Mermaid構文の表示確認を完了条件として明記する。
- 1つの文書更新と一体で作成できる小規模な図は同じタスクに含め、複数の図や複雑な図で独立した確認が必要な場合だけ別タスクへ分割する。
- 既存文書に図の記法や構成上のルールがある場合は、その形式に合わせる。

## 作業ルール

- 実装は行わない。
- `specs.md` は変更しない。
- `plan.md` は変更しない。
- 仕様や実装方針を再定義しない。
- 未確定事項を推測で解決しない。
- 実行していないテストや検証を完了扱いにしない。
- 既存コードや既存文書から確認できない内容は「要確認」として扱う。
- Mermaid図に含める構成要素や関係を推測で補完しない。
- `tasks.md` のチェックボックスは未完了の `[ ]` で作成する。

## 自己レビュー

出力前に次を確認する。

- すべてのタスクが `specs.md` または `plan.md` に根拠を持つか。
- `specs.md` の受け入れ条件を確認できるタスクが含まれているか。
- `plan.md` の変更対象がタスクへ反映されているか。
- `plan.md` の変更しないものや対象外がタスクに混入していないか。
- 前提確認、実装、テスト・検証、ドキュメント更新、完了確認が分離されているか。
- タスクの順序と依存関係が現実的か。
- 並列実行可能なタスクに `[P]` が付いているか。
- 各タスクが1つの目的に集中しているか。
- 各タスクの完了を客観的に確認できるか。
- 変更しない対象への不要な実装タスクや、不要なADR作成が追加されていないか。
- ドキュメント更新で図を用いると理解しやすい箇所について、必要なMermaid図の作成または更新がタスクに含まれているか。
- Mermaid図を含むタスクに、図の目的、本文との整合確認、構文の表示確認が含まれているか。
- 不要なMermaid図を形式的に追加していないか。
- テンプレートの必須項目が欠けていないか。

## 完了時の報告

次の内容を簡潔に報告する。

- 作成したファイル
- タスク数と実装単位別の内訳
- 実装開始前に解決が必要な事項
- 並列実行可能なタスク
- `specs.md` または `plan.md` との不整合や不足事項
